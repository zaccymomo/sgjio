# Decisions made during setup

Several Sprint 1 stories leave a value open for the team to decide. The setup tasks had to pick something to build on, so each one below is a **proposed default**. Every value is a single setting in `api/.env` (or one constant), so changing one after the team discusses it takes minutes.

| Session length, main app                  | SCRUM-62           | Signed out after **7 days without use**. Already fixed by the stories, and built as written:

- Reset links are valid for **5 minutes**, work **once**, and a new request cancels earlier links (SCRUM-63, SCRUM-69).
- Sign-in and "forgot password" never reveal whether an email has an account or is an administrator (SCRUM-62, 63, 68, 69). Failed attempts on unknown emails are blocked the same way, for the same reason.
- **Registration is the one place that does say an email is already in use** (SCRUM-61 AC2 asks for it, so the person can be sent to sign in instead). Sign-in and "forgot password" still do not, so neither of those pages can be used to check who has an account.
- Registration never creates administrators. New accounts are always ordinary users, and `/register` exists only on the main app, not the admin portal (SCRUM-68).

## Other setup choices

- **Blocking is per email, per front end.** Five failures on the main app do not block the same person on the admin portal. Blocking by IP address as well was left out: on a campus network many people share one address.
- **Email in development goes to Mailpit**, so nobody receives a real email while testing. For a demo, set the `SMTP_*` values in the server's `.env` to a real provider (for example Resend, SendGrid or Brevo; all have free tiers).
- **Figma frames are phone-width, but SGJio is a web app.** Below 768px the tabs sit at the bottom, as in Figma. From 768px up they move into the header and the content is centred.
- **Reordering sends the whole list, and the order it replaces.** Reordering topics sends every active topic, and reordering lessons sends every lesson in that topic (any status), or every lesson with no topic, both in the new order and in the order the page was showing. If that is not the order now, because another administrator or another tab has added, removed or reordered something since, the server refuses with `order_out_of_date` and the page loads the latest order, rather than silently undoing someone else's change. This is also why reordering is switched off while searching or filtering.
- **New and restored topics go to the end.** A restored topic does not return to its old place, which other topics may have taken since. Lessons are reordered only within their topic; moving a lesson to another topic belongs to the lesson editor.
- **Positions are not unique.** Every read breaks ties by creation time, so a duplicate (for example, two lessons created at the same moment) cannot break a page. Reordering never changes a lesson's "last updated" time.
- **Saving a draft names the version it replaces.** The lesson editor sends the "last updated" time it loaded with every save and delete. If the lesson has changed since, in another tab or by another administrator, the server refuses with `lesson_out_of_date` instead of overwriting that change, and the editor keeps what you typed. Reordering does not change "last updated", so it never makes an open editor out of date. A save that changes nothing leaves "last updated" alone.
- **The editor saves by itself (SCRUM-19).** Users only ever see published versions, so drafts save a moment after each change, one save at a time, and leaving the editor saves first. A new lesson is only created by its first change, so opening the editor and leaving never leaves an empty one behind. Only a lesson that has **never been published** can be deleted, because deleting a lesson also deletes everyone's completions of it.
- **The rules for a lesson live in one place.** Every save returns the lesson's issues (what blocks publishing, and warnings), worked out on the server by `api/app/lesson_doc.py`; the editor only shows them. The import command and the seed apply the same rules.
- **Lessons can be written as files** in `content/lessons` and loaded with `python -m app.cli import-lessons --publish`, which the seed also runs. Files hold a lesson's content; where it sits (topic and position) is the administrators', so loading files never undoes a reorder. The first load adopts an existing lesson with the same title instead of duplicating it.
- **Archived topics in the lesson editor.** A lesson cannot be moved into, or created in, an archived topic (`topic_archived`). A lesson already in one keeps saving there, so archiving a topic never stops someone finishing a draft. Changing a lesson's topic puts it at the end of the new topic.
- **The admin portal uses a data router; the main app does not.** `admin/src/App.tsx` builds its routes with `createBrowserRouter`, because the lesson editor's unsaved-changes warning needs React Router's `useBlocker`, which only works with one, and is the only way to catch the browser's back button as well as links. The routes are still written as JSX, as in `web/src/App.tsx`. The main app can switch the same way if it ever needs it.
- **Leaving a lesson steps back to its topic (SCRUM-53).** A lesson opened from a topic page goes back in the browser history when it closes or finishes, instead of opening the topic page again on top. The history stays home → topic, so the browser's back button then leads home (AC4). A lesson opened any other way replaces itself with its topic.
- **Lesson times match the lesson's cover.** The topic list says "About 2 min" as the cover does (`readingLabel`), not Figma's "Under 2 min", so the two never disagree.
- **A topic's description appears in one place for learners (SCRUM-86):** under its name on the topic page. The progress circles are too small for a sentence, and a lesson's cover already has the lesson's own summary. Administrators write it in the topic's Edit dialog (the menu item that was Rename) and see it at the top of the opened topic. Admin search still matches topic names and lesson titles only. The seed fills in a description only while a topic has none.
- **"Last attempted" means last finished (SCRUM-54).** Only a finished run through a lesson is recorded, so one left half way still reads "Not attempted yet". The date is shown in the browser's time zone. A completion from before attempts were recorded (for example a seeded one) uses its completion time. The best score is shown as stored, out of the questions answered then, so a lesson revised since keeps the total its best was scored on.
- **How lesson insights are counted (SCRUM-84).** Figures are per published version and count learners only, never administrators. "Right first time" and how often each option was chosen come from each learner's **first finished run** of the version, because a retake comes after the explanation and would hide a confusing question; the average best score uses each learner's best run of the version. Unfinished runs count only towards the finish rate and "where learners stop". One-option taps are left out, as they are of scores.
- **Nothing for fewer than 5 learners, at any level (SCRUM-84 AC3).** The rule applies to a version as a whole and to every smaller group the page shows: newcomers or Singaporeans alone, the learners who retook a question, and each week of a running figure. Below 5, the figure is left out, not rounded. No response carries a learner's name, email or id (AC5).
- **Insights are per version, with the version before beside them.** The page opens on the latest version; the one before is shown as a change ("▲ 9 pts on version 1") when it has figures too. The weekly chart starts each version where its first learners finished it, rather than at its publish date, so the step from one version to the next is where learners actually met it.
- **Insights for every kind of learner, not each person.** The page can be filtered to newcomers or Singaporeans (`users.user_type`), and each question shows both side by side. It never lists individual learners or their scores; an administrator rewriting a question needs to know how it was answered, not by whom.
- **Demo learners are a command, not part of the seed.** `python -m app.cli demo-activity` adds 60 demo learners and their runs (see `docs/data-model.md`). It stays out of the seed so tests and teammates' databases are not filled with fake learners, and so it can be re-run on a demo morning to bring the dates up to today.
- **Error red is not brand red.** Figma's red (`#F43F5E`) is used for highlights. Form errors use a deeper red (`#DC2626`) so an error never reads as decoration.
